04

72 分钟到底讲了什么

内容本身是好东西。我按官方文档和教程，把五个主题各用几句话讲清楚：

① 第一个 Agent：其实就是几个字段

在谷歌的开源框架 ADK（Agent Development Kit）里，一个 Agent 就是一组配置：名字、模型、描述、指令、工具。Codelab 里的第一个例子，就是一个会用 Google 搜索的“行程规划 Agent”，几十行代码。

② 记忆：分三层，最容易忘的是“重启”

官方 Codelab 把记忆分成三层：Session 是一次对话的容器，装着说过的话；State 是挂在 Session 上的键值“便签”，比如 destination=Tokyo；MemoryService 是长期存储，放用户偏好这类要一直记住的东西。

坑在于，默认的 InMemorySessionService 把一切放在内存里，程序一重启就全忘了。换成 DatabaseSessionService（本地用 SQLite），对话才能活过重启。Codelab 里的原话是：

Use DatabaseSessionService for production. It ensures user conversations survive server restarts and enables long-term history analysis.
中文：生产环境用 DatabaseSessionService。它能保证用户对话在服务器重启后依然存在，也方便做长期的历史分析。

③ 长时运行：让 Agent 学会“睡觉”

谷歌博客用了一个新员工入职的例子：发欢迎包，等几天让员工签文件，交给 IT 子 Agent 开账号，再等几天收电脑，最后发第一天日程。整个流程跑几周。

博客的思路是三条：用明确的状态机记录“进行到哪一步”（文中定义了 6 个状态，从 START 到 COMPLETED），而不是让模型翻聊天记录；等待期间不轮询，由 webhook 把 Agent 叫醒；把专门的活交给子 Agent。最打动我的是这一句：

The fix isn’t a bigger context window. It’s a fundamentally different architecture.
中文：解决办法不是更大的上下文窗口，而是一种根本不同的架构。

④ MCP 和 API：区别在“能不能被发现”

按 Google Cloud Tech《Building your own MCP server with ADK》这一期的讲法，自己做一个 MCP 服务器，核心是两个处理函数：list tools 告诉客户端“我有哪些工具”，call tool 在客户端调用时执行。本地用 stdio 连接，远程常用 streamable HTTP。

它和普通 API 的区别，视频里说得很直白：包成 MCP 之后，任何遵循 MCP 的客户端都能接进来，不只是 ADK 写的 Agent。换句话说，API 是你写好对接代码才能用，MCP 是工具自己报家门。

⑤ 多 Agent：靠一张共享的“便签”传话

Codelab 里有个很好懂的例子：一个“美食 Agent”找餐厅，把结果写进 State 的 destination；后面的“交通 Agent”在指令里写 {destination}，自动读到这个值，再给出路线。两个 Agent 用 SequentialAgent 按顺序串起来。入职那个例子则是另一种：主 Agent 把开账号的活转给 it_agent，做完再交回来。

05

这种帖子为什么总能火

有人说，搬运也是一种传播，至少让更多人知道了这些教程。也有人觉得，不标出处、把旧内容说成“刚刚发布”，对原作者和读者都不公平。

我的看法是：内容是真的，包装是假的。“谷歌”“刚刚”“1 小时”“替代付费课”，每个词都在制造“现在不收藏就亏了”的感觉。但真正想学的人，最需要的恰恰是剪辑版丢掉的东西：每一期的配套代码、动手实验和文档链接。

这件事和我们有什么关系

对写代码的人

直接去看原版：视频简介里有 Codelab 和文档链接，入职 Agent 的完整代码在 GitHub 上。看一遍不如跟着 Codelab 跑一遍，重启后 Agent 还记得你，这一步做完才算真懂了记忆。

对做内容的人

转发“某大厂刚发布”之前，花三分钟做三件事：看进度条和文案对不对得上，看画面里有没有片头片尾和集数，按文案搜一下最早谁发过。我这次就是这么查出来的。

对想入门的人

建议顺序：先看播放列表里的设计模式和记忆，再做 Codelab，然后看 MCP，最后读长时运行的博客。一天一期，两周左右能走完。
