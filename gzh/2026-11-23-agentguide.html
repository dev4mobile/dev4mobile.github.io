01

ADK 里的 Agent 分几种

谷歌的开源框架 ADK（Agent Development Kit）把 Agent 分成三类，视频里用公司打比方：

LLM Agent：大脑

由 Gemini 这类大模型驱动，自己决定用哪个工具、下一步做什么。

Workflow Agent：经理

不靠模型做决定，按固定规则调度子 Agent，有三种：Sequential（顺序，像流水线）、Parallel（并行，像同时调用几个 API）、Loop（循环，重复到完成为止）。

Custom Agent：专家

继承 BaseAgent，用自己写的 Python 逻辑，适合需要完全掌控流程的场景。

多个 Agent 组成一棵树：根 Agent 像 CEO，子 Agent 像副总、经理和员工。有一条硬规则：

they follow single parent rule that is each sub agent only have one parent agent.
中文：遵循单一父节点规则，每个子 Agent 只能有一个父 Agent。

02

6 种设计模式，什么时候用哪个

制图：AI人工智能大师，内容整理自 Google Cloud Tech 两期设计模式视频

单 Agent：原型够用，复杂了就飘

一个模型配上工具（演示里只给了 Google 搜索），靠模型自己的推理决定步骤。问题是任务一复杂，提示词就会变得很长，而模型输出本身不确定，行为会变得很不可靠。

顺序 + 并行：最常用的组合

顺序 Agent 适合步骤固定、要反复跑的任务：先让「找美食 Agent」挑餐厅，再让「交通 Agent」规划路线，前一个的输出就是后一个的输入。代价是不灵活。

并行 Agent 让博物馆、演出、餐厅三个查找 Agent 同时跑，延迟大幅降低，但同时跑多个 Agent 前期成本更高，而且通常还要一步汇总。所以视频里的常见做法是：并行查完，再接一个汇总 Agent，用顺序 Agent 串起来。

循环：生成 + 评审，直到合格

例子里的条件是「酒店和活动场地车程在 30 分钟以内」。生成 Agent 出方案，评审 Agent 按条件检查，不合格就带着反馈打回去重做。

This loop will continue until the plan is approved or we hit a maximum number of iteration to prevent infinite loops.
中文：循环会一直进行，直到方案通过，或者达到最大迭代次数，以防无限循环。

代价是更慢、更贵，退出条件必须设计好。

协调者 vs Agent as Tool：差在控制权

协调者像项目经理：分析请求，转给对应的专家子 Agent，子 Agent 接手后拿到全部控制权。演示里，「寿司加路线」被转给美食交通 Agent，「再找个博物馆和演出」被转给附近地点 Agent。代价是路由这一步也要调用模型。

Agent as Tool 则是主 Agent 始终掌控全局，把子 Agent 当成一个无状态的工具来调用。视频的比喻是：协调者是把项目交给员工的经理，Agent as Tool 是拿起一件趁手工具的工匠。

官方的选型建议：单 Agent 做简单原型；顺序/并行用于需要可靠、结构化的流程；循环用于要满足特定条件的任务；需要灵活路由时用协调者或 Agent as Tool。

03

Agent 之间怎么传话

三种机制：

共享 Session State：一块白板

一个 Agent 把结果写进 State，另一个 Agent 读出来。比如让 A 只输出餐厅名，映射到 destination 这个 key；B 的指令里写 {destination}，就能自动拿到这个值。

LLM 驱动的委派

协调 Agent 像 CEO，自己判断该交给哪个子 Agent。例子：「开一张发票」会交给账单 Agent。

显式调用（AgentTool）

把目标 Agent 包装成工具，像调用函数一样调用它。例子：做分析的父 Agent 遇到算数，就调用一个计算器 Agent。

子 Agent 和 Agent as Tool 的区别：子 Agent 是组织架构里的人，始终归父 Agent 管；Agent as Tool 像外请的顾问，不在你的核心架构里。

04

三层记忆，一层比一层记得久

制图：AI人工智能大师，内容整理自 Google Cloud Tech 记忆系列三期视频

第一层：Session 和 State

Session 就是一次连续的对话，像手机里的一个聊天窗口。它有两部分：Events 是完整记录，每条用户消息、每条 Agent 回复，连用户发的图片都在；State 是一张小便签，存餐厅名、确认号这类单个值。

Because you don't want your model to reread 15 messages just to find one value.
中文：因为你不想让模型为了找一个值，把 15 条消息重读一遍。

演示里，第一轮让 Agent「规划两天里斯本行程」，第二轮如果新建了 Session，Agent 就把城市、第一天的安排、用户兴趣全忘了。解决办法：同一个 Session 跨多轮复用。

还有一条容易踩的坑：不要在工具代码里直接改 Session 对象，否则这次修改不会进事件日志，持久化服务之后也不会保存它。正确做法是通过 ADK 传给工具或回调的 context 写 context.state，ADK 会把这次修改和事件一起记录下来。

第二层：活过重启

默认的内存 Session 服务一重启就清空，像 RAM。换成 DatabaseSessionService，每条消息、每条回复、每次 State 变化都写进数据库（可以是本地文件，也可以是 Postgres）。用户带着同一个 Session ID 回来，历史和最新 State 都能加载回来。写法是先 get session，存在就接着用，不存在再 create。

In summary, the session service is pluggable and your agent logic can stay the same.
中文：总之，Session 服务是可插拔的，你的 Agent 逻辑不用改。

三种可选：内存版（重启清空）、数据库版（数据库归你管）、Vertex AI 版（托管在谷歌云）。

光有对话记录还不够，视频又加了一张用户偏好表：每个用户 ID 加一个偏好 key 占一行，比如饮食、出行方式。配两个工具，recall 读出全部偏好，save 新增或更新；工具拿到的 context 里带着当前用户 ID，读写不会串号。给 Agent 的指令顺序是：先 recall，再规划，最后 save。演示里用户说「记住我吃素」，模拟重启、换一个全新的 Session ID 之后，Agent 仍然读到了「dietary = vegetarian」。

第三层：Memory Bank，按意思检索

Session 服务管的是正在进行的对话；MemoryService 管长期归档，视频叫它文件柜。

本地测试可以用内存版 MemoryService，但它不跨重启保存，只支持关键词搜索。Vertex AI Memory Bank 存在云端，支持语义搜索：搜「两轮交通工具」能找到关于自行车的记录。它会用 Gemini 从内容里提炼事实，再生成向量。

It is important to remember that this is not just a table. It is a service that processes content, finds useful facts, and make them searchable.
中文：要记住，它不只是一张表，而是一项服务：处理内容、找出有用的事实、让它们可以被检索。

写入有两种：会话结束时调用 add_session_to_memory 整段归档，包括文字和图片、视频、音频的引用；或者直接上传图片、视频、音频加一段文字说明，生成事实存进去。读取靠 PreloadMemoryTool：每一轮开始时，它读用户的新消息，去 Memory Bank 做语义搜索，把最相关的事实注入提示词。

演示里，用户在第一个对话里发了一张历史建筑的照片、一段海边视频、一条小镇的语音；到了一个全新的空对话里问「推荐个有文化的目的地」，Agent 直接调出了「喜欢历史建筑、喜欢海边、去过某个小镇」。

05

MCP：Agent 怎么接外部工具

Think of it as MCP is a USB-C port for AI.
中文：可以把 MCP 理解成 AI 的 USB-C 接口。

MCP 是一个开放标准，规定大模型和 Agent 怎么跟外部世界打交道。MCP Server 暴露工具（文件系统、数据库、Google 地图、Imagen 生图……），MCP Client 发现并使用这些工具。大多数情况下，你的 ADK Agent 就是 Client。

在 ADK 里怎么接

靠 MCPToolset。它负责建立连接（本地进程或远程 HTTP 服务器）、加载所有可用工具、把 MCP 工具转成 ADK 能用的格式；运行时把请求转给 MCP Server，再把结果交回 Agent。

视频里两个例子：一个是用 NPX 命令启动文件系统 MCP Server，把目标文件夹路径作为参数传进去，Agent 就有了列目录、读文件的工具；另一个是 Google 地图 MCP Server，配好 API Key、开通相应的地图 API 后，Agent 就能回答「从纽约到旧金山怎么走」。

好处有三点：复用（MCP Server 可以是独立服务，任何兼容 MCP 的客户端都能接，不用写胶水代码）、安全可控（能划清边界）、部署简单（工具和 Agent 解耦，可以单独在 Cloud Run 或 GKE 上扩容）。

MCP 和 API 到底差在哪

这一期由 Smitha Kolan 主讲。API 是程序和程序之间的代码级合约：请求格式固定，两边都得事先知道对方要什么。MCP 是模型和环境之间的语义协议：模型能自己发现一个工具能做什么、要什么输入、返回什么。「什么时候调用什么」这层逻辑，从应用代码挪到了模型的推理里。

她举的例子是一个处理工单的 Agent，要接 Gmail、Notion、Jira。走 API，每个集成都要写定制代码，处理分页、鉴权、报错、限流；走 MCP，每个服务暴露兼容接口，模型自动发现。MCP 不替代你的后端，MCP Server 像一个翻译，把现有 API 转成模型能理解的格式。

APIs were made for deterministic systems, one program asking another for data, and MCP is made for probabilistic systems, a model reasoning about what it can do.
中文：API 是为确定性系统设计的，一个程序向另一个程序要数据；MCP 是为概率性系统设计的，一个模型在推理自己能做什么。

她也列了 MCP 的挑战：普及程度、安全与权限控制（需要清晰的权限层），以及开发者思维的转变。

TAKEAWAY

这件事和我们有什么关系

对写代码的人

先别急着上多 Agent。单 Agent 能跑通就先用单 Agent，哪一步不稳定，再把那一步拆成顺序、并行或循环。记忆同理：先把 Session 复用对，再上数据库，最后才需要 Memory Bank。

对用 AI 做自动化的人

「记住我的偏好」不用靠一段越来越长的提示词：一张按用户 ID 存的偏好表，加上「先 recall、最后 save」两条指令，就能让 Agent 在新对话里也认得你。

对想入门的人

视频简介里都附了 Codelab：记忆系列对应 goo.gle/agentmemorylab，设计模式对应 goo.gle/agenticpattern，MCP 对应 goo.gle/mcpclient。看完一期就跑一期。

博主点评

这 9 期最有用的不是哪个 API，而是一套判断顺序：先问任务是固定流程还是要动态路由，再问要记多久，最后问工具要不要给别的 Agent 复用。三个问题想清楚，架构基本就定了。

你现在做的 Agent，卡在哪一步：不稳定、记不住，还是接不上工具？
